Architecture

How Atlas works under the hood

Atlas is built around an event-driven architecture with clear separation of responsibilities. The core philosophy is that Atlas coordinates, but does not control. Modules communicate through events rather than direct coupling.

Architecture Flow

Core Classes

Atlas

The public entry point. Creates core services, initialises modules, exposes the API.

EventBus

Central communication hub. Publish/subscribe pattern for loose coupling.

Events: store:filtersChanged, store:searchChanged, store:sortChanged, store:layoutChanged

Registry

Discovers and validates HTML. Finds [data-directory], [data-member], and controls. Exposes read-only API.

Store

Manages application state (filters, search, sort, layout). Publishes events when state changes. Includes filter caching for performance.

MemberCollection

Manages member data. Provides query methods (filter, search, sort, unique values). Uses Set lookups for O(1) filter matching.

Renderer

Updates the DOM. Listens to Store events, batch updates using DocumentFragment, manages loading state, and handles lazy rendering for large directories. Contains no business logic.

Modules

  • FilterGenerator — Generates filter UI from member data. ARIA-enabled, keyboard accessible.
  • FilterChips — Displays active filters as removable chips. ARIA-enabled, keyboard accessible.
  • ResultCounter — Shows "Showing X of Y members" with ARIA live region.
  • SortGenerator — Generates sort controls (three-state toggle). ARIA-enabled, keyboard accessible.
  • LayoutManager — Manages grid/list layout switching with persistence.

Performance Optimisations

Atlas is designed to perform well with large directories. The following optimisations are built in:

Filter Optimisation

  • Set lookups: Filter values use Set for O(1) lookups instead of O(n) array searches
  • Filter caching: Results are cached by filter state — repeated filters are instant
  • Early exit: If any field has no values, filtering stops early

Lazy Rendering

  • Automatic: Lazy rendering activates automatically when a directory has more than 300 members
  • Intersection Observer: Only members visible in the viewport (plus a buffer) are rendered in the DOM
  • Batch rendering: Members are loaded in batches of 25 as you scroll
  • Memory efficient: Off-screen members are removed from the DOM, keeping memory usage low

Sort Optimisation

  • Intl.Collator: Uses native browser collation for faster, locale-aware string comparison

Accessibility

Atlas is built with accessibility as a core principle:

  • Keyboard navigation — All interactive elements (filters, sort buttons, chips, Clear All) are keyboard-accessible using Tab, Enter, and Space
  • ARIA attributes — Proper roles, labels, and states for screen readers
  • Focus states — Visible focus rings for keyboard users (:focus-visible)
  • Reduced motion — Respects prefers-reduced-motion system setting
  • Live regions — Result counter announces changes to screen readers

Mobile Optimisation

Atlas is optimised for mobile devices:

  • Touch targets — All interactive elements have a minimum 44px tap target
  • Responsive grid — Grid columns adjust automatically on smaller screens
  • iOS zoom prevention — Search inputs use 16px font size
  • Stacking — Filters stack vertically on small screens
  • Responsive layouts — Sidebar and two-column layouts stack on mobile

Event Flow Example

User clicks a filter button:

  1. FilterGenerator detects click
  2. FilterGenerator calls Store.toggleFilter()
  3. Store publishes 'store:filtersChanged'
  4. Renderer listens → re-renders members
  5. ResultCounter listens → updates count
  6. FilterChips listens → updates chips

User types a search query:

  1. Search input fires 'input' event
  2. Atlas calls Store.setSearch()
  3. Store publishes 'store:searchChanged'
  4. Renderer listens → re-renders members
  5. ResultCounter listens → updates count

Rendering Philosophy

Atlas uses batch rendering:

  1. State changes → Store publishes event
  2. Renderer receives → computes new state
  3. DocumentFragment → builds DOM updates in memory
  4. Single DOM write → appends fragment

This minimises reflows and repaints.

Loading State (No Flicker)

  1. HTML starts with data-atlas-loading attribute
  2. CSS hides the directory
  3. Atlas initialises and renders members
  4. Atlas removes data-atlas-loading
  5. CSS fades in the directory

Design Principles

  • HTML First — Configure through HTML, not JavaScript
  • Everything Is Data — Members are structured data
  • HTML Is The Database — Read once, cache everything
  • Semantic Names — No platform-specific identifiers in core
  • Separation of Responsibilities — One class, one job
  • CSS Owns Presentation — CSS decides appearance
  • JavaScript Owns Behaviour — Search, filter, sort, state
  • Zero Dependencies — No third-party libraries
  • Performance Is A Design Requirement — ~1,000 members
  • Accessibility Matters — Keyboard, screen reader, reduced-motion
